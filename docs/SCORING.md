# 评分规则与评分模型

平台给每个案例打三项分：**R**（子技能分发）、**A**（工具参数）、**J**（联合）。优化器以这些分数为目标改 Skill，
所以评分规则决定了「往哪里优化」。本页说明工具参数（A）怎么判对错，以及如何让大模型参与判断。

## 结束协议与业务结果分开

`finish` 是执行协议状态，不是业务正确性的替代品。未开启严格结束协议的环境默认允许模型在已经完成业务工具调用后用普通终止回复结束；这类案例按实际路线、业务工具和参数评分，同时记录 `finish_protocol=missing`。没有业务工具调用、也没有可靠的澄清或无需操作结构化证据时，结果为“无法判定”，不会自动通过。将执行环境的“严格结束协议”打开后，缺少 `finish` 才会作为 `protocol_error` 失败。无论模式如何，截断、超时、步数耗尽和 `finish` 摘要与事件不一致仍然是失败。

测试与试跑使用相同口径。历史结果保持原样；新运行使用新的基线缓存标识，旧口径基线不会自动复用，需要重新运行基线。

## 谁来判断什么

| 判断项 | 判断方式 |
| --- | --- |
| 选了哪些子技能、顺序 | 代码 |
| 调了哪个工具、调用次数与顺序 | 代码 |
| 必填字段是否齐全、有没有多余字段 | 代码 |
| **参数的值对不对** | 由「参数比较方式」决定，可交给评分模型 |

结构性的判断按已配置规则用代码执行；只有「值是否表达了同一个意思」才可能需要大模型。

## 参数比较方式

在「Prompt 与模型」页面的执行环境「优化与验收 → 评分规则」中设置，随环境版本冻结；改动后需要重新跑基线。

| 方式 | 何时算对 | 例：预期 `{"color":"蓝色调"}` |
| --- | --- | --- |
| 语义（大模型判断） | 评分模型认为意思一致 | `"偏蓝的色调"` ✓，`"红色"` ✗ |
| 宽松 | 归一化后相等：去首尾空格、全半角、大小写，`"3"==3`、`"true"==true`，ISO 时间，数组不计顺序 | `" 蓝色调"` ✓，`"偏蓝的色调"` ✗ |
| 只看字段 | 字段都在即可，不看取值 | `"红色"` ✓，缺 `color` ✗ |
| 严格 | 逐值完全相等（旧版口径） | 只有 `"蓝色调"` ✓ |

- **允许多余字段**：模型多传了预期里没有的字段是否算对。严格默认不允许，其他方式默认允许。
- **字段单独规则**：对某个字段路径指定不同方式，可限定工具名。路径与案例对比里显示的一致，`[*]` 匹配任意下标、`*` 匹配任意字段名。
  可选 严格 / 宽松 / 只看字段 / 语义 / **不比较**（该字段可缺省、取值不限）。
  例：整体用语义，`$.args.method` 设为严格；自由文本字段 `$.args.prompt` 设为不比较。
- 业务参数规则由 Skill 提供，评分以案例 expected 和比较规则为依据，不再使用独立工具 Schema；调用名称和参数对象仍进行基本结构检查。
- 新建环境默认「宽松」；之前创建、没有配置过评分规则的环境保持「严格」，历史成绩不变。

## 评分模型

在「评分模型」中配置标准 API（URL、模型 ID、API Key）或 WebSocket 网关，填写方式与业务模型相同，可用「测试连接」检查。
标准 API 评分模型可在「高级：评分请求」中设置「流式返回」。新建评分模型默认开启；已保存的显式设置保留。连接测试、保存发布与正式评分使用同一设置。只接受流式请求的模型网关需要开启此项；HTTP 404 本身也可能表示 URL 或模型路由错误，应结合网关日志确认。修改后发布新的执行环境并重新运行评测，已启动运行的配置快照不会改变。流式响应会先聚合完整正文，再解析评分 JSON，不改变评分规则。

它只用来判断参数值，与业务模型、优化模型相互独立，建议不要与被评的业务模型使用同一个模型。

一个案例里所有需要判断的值合成一次请求发给评分模型，返回每一项「一致 / 不一致」和不超过 40 字的理由。以下情况不调用模型：

- 数据集为该字段写了关键词，且关键词按字面全部出现在实际值里；
- 实际值与预期值在宽松规则下相等。

**稳定性**：温度固定为 0；判定按「评分模型 + 判定规则版本 + 字段 + 预期值 + 实际值 + 判断依据」缓存，相同缓存键命中时复用已有判定，不再重复发起请求。缓存减少同一输出的重复评分差异，但首次判定仍可能误判，也不能消除业务模型采样变化。更换模型身份或判断依据后使用新的缓存键。

**失败处理**：评分模型调用失败或答复不完整（漏判、不是 JSON），该案例记为基础设施错误，不计入指标分母，也不会被当作对或错，
运行记录顶部会提示。评分模型用量计入实际消耗统计。

**未配置评分模型**：运行环境的整体或字段规则选了语义比较，但没有评分模型时，正式运行与带预期的案例试跑会在预检阻止（judge_not_configured）。先配置评分模型并发布新环境，或选择确定性比较方式；不要把缺少评分模型当作自动降级通过。

## 案例级语义规则的当前限制

当前预检检查的是环境 scorer_config.compare 的整体/字段语义设置，尚未逐案检查合并后的有效规则。若环境未启用语义、只有某案例 expected.compare 启用 semantic，而且没有评分模型，该案例仍可能走 semantic_fallback，按宽松比较处理，**不会调用评分模型**。正式运行与带预期试跑都存在这个边界。

使用案例级语义覆盖时也应显式配置评分模型，并核查判定事件；不能只靠运行未报错证明做了模型评分。这个限制尚未在代码中修复，本页记录实际行为，不将回退结果称为真实语义评分。本文真实任务协作教程在环境字段规则中启用 semantic 并配置 judge，不依赖此回退。

## 在数据集里写判断依据

在案例上加 `judge`，键是字段路径：

```json
{"query": "把图调成蓝色", "skill": "image_color_transfer",
 "tool": {"name": "editImage", "args": {"targetColor": "蓝色"}},
 "judge": {"$.args.targetColor": {"keywords": ["蓝"], "requirement": "表示蓝色系即可"}}}
```

- `keywords`：实际值体现这些关键词的含义即算对；字面全部出现时直接通过。
- `requirement`：一句话判断要求，评分模型以它为准。
- 两者至少写一个。

单个案例也可以用 `compare` 覆盖环境设置（`version` 必须是 `compare-v2`）：

```json
{"query": "...", "skill": "...", "tool": {...},
 "compare": {"version": "compare-v2", "mode": "strict",
             "field_rules": [{"path": "$.args.prompt", "mode": "ignore"}]}}
```

## 在哪里看结果

- 案例详情「参数差异」中，评分模型判错的字段会附上理由；「评分模型判定」列出每个被判断的值、结论与理由。
- 运行记录中评分模型的调用显示为「评分模型 · 调用模型」，每个案例有一条「评分模型完成判定」汇总（含缓存复用数）。
- 优化器收到的失败证据包含这些理由。

## 风险提示

- 大模型判断有被「钻空子」的可能：如果只写关键词，候选可能学会把关键词堆进参数。关键依据请用 `requirement` 写清楚，
  对必须精确的字段（方法名、枚举、ID）设字段规则为「严格」。
- 评分模型的判断不是事实标准，定期抽查「评分模型判定」中的理由；发现误判时修正数据集的判断依据并发布新版本。

## 判定依据

每条不通过的原因都带一条「依据」，说明它按什么规则算错，例如：

- `create_task 的参数 priority 不对：给了 urgent，应为 high` — 依据：严格比较：值必须与数据集预期完全相等；
- `assign_task 缺少参数 assignee_id（应为 U7）` — 依据：数据集预期包含这个字段；
- `create_task 缺少必填参数 title` — 依据：工具 Schema 把这个字段列为必填（required）；
- `参数 color 不对` — 依据：语义比较……；评分模型：红色与蓝色含义相反；
- `执行出错：步数用尽仍未完成` — 依据：模型返回：……。

依据记录在诊断的 `basis` 字段，显示在案例对比、案例详情、试跑结果和运行记录中，也随失败证据交给优化器。

## 实际调用、返回与历史展示

实际工具调用按执行事件记录，工具返回按 fixture 是否命中记录。fixture_miss 时保留已尝试的工具名和参数，显示未取得模拟返回；不能把它展示成“无需操作”或“未调用工具”。它仍属于执行失败，不因参数列表可见而通过。

案例详情的“预期与实际”包含参数、已记录的工具返回及最终回复。后两者用于解释执行，不直接计入参数评分。旧记录可从同一案例、阶段和重复轮次的事件恢复缺失展示；不会伪造未保存的回复，也不重算历史分数。
