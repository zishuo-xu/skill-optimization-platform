# 日常测试与独立验收分离

## 流程与语义

日常只需要测试集：运行评测 → 根据失败修改 Skill → 在同一测试集重跑候选。新导入未指定用途的案例全部进入测试集，不自动扣出验证或最终测试比例。已有明确用途保持不变。

内部 split=optimize 对应界面的“测试集”；validation 对应“独立验收集”；final_test 保持独立最终测试。字段名保留，避免将用途变化混入数据迁移。

- evaluate：只评测测试集，不调用优化器。
- optimize：只向优化器提供测试集失败证据，生成候选并在测试集重跑；不要求独立验收集，不执行正式验收、不产生 accept。
- validate：用户选择已有候选启动正式验收；只对独立验收集运行基线与候选配对评测，沿用既有验收规则。
- final_test：保留独立的最终测试通道，不参与日常修改或候选选择。

普通测试成绩说明已知案例表现；只有正式验收达标的候选才可通过现有应用入口设为当前版本。未验收候选仍可查看差异及案例执行链路。不会以普通重跑结果替代正式验收证据。

## 数据与版本边界

可在日常优化完成后再补充独立验收集。验收绑定来源优化运行的候选与基线，要求当前 Skill 和执行环境仍匹配，并冻结当前验收数据版本。拒绝验收案例与源测试数据/最终测试数据在案例 ID、归一化问题或分组上重复。

这些检查可以拦截可识别的数据复用，不能自动证明语义不同表述一定独立；正式验收案例应由使用者独立准备。正式验收内容和结果不加入后续优化器上下文，验收不生成新候选。应用继续使用版本比较、完整性检查与人工操作。

## 验收计划

验证仅测试集可评测与优化、后补验收集可配对验收并应用、三类用途互不串跑、重复案例拒绝、版本冲突拒绝、未验收候选禁止应用。使用隔离 Demo 数据进行 PC 页面验收，不调用真实业务服务。

## 验证结果

- 精确提交快照：542 项 Python 回归通过，24 项 Node 测试通过。
- PC 浏览器 1280×800：仅测试集普通评测、优化生成候选并重跑、缺少验收集时引导、选择独立验收用途上传并发布、回到候选启动正式验收、验收通过后人工应用全部跑通；未出现横向溢出。
- 使用本地隔离 Demo 数据，日常测试 33 例，后补独立验收 8 例、每例配对重复 3 次。此证据验证产品流程与隔离机制，不代表外部模型的真实优化效果。
- 测试覆盖案例 ID/问题/分组重复拒绝、验收前候选篡改拒绝，以及应用预检后的数据版本竞争仍由原子更新拒绝。
