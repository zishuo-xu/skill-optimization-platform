# 核心概念与产品边界

平台的目标是提升 **Skill 执行任务并调用工具的准确率**。输入是一套业务规则和测试数据，输出是有执行证据、可对照、可接受或拒绝的 Skill 新版本。它把 RSI 思路落实为受评测约束的迭代，不训练或微调模型。

## 两个循环

**执行循环**发生在一个案例内部：模型读取主 Skill → 按需加载子技能 → 生成工具调用 → 获取模拟返回 → 根据结果继续或结束。例如创建任务后，从返回中读取新任务 ID，再分派给负责人。每一步的模型请求和工具结果都可检查。

**优化循环**发生在版本之间：用测试集执行 → 评分与归因 → 优化模型提出 Markdown 补丁 → 静态检查 → 候选在同一测试集重跑。用户可继续下一轮；准备发布时，才进入独立验收与应用。

```mermaid
flowchart LR
  S[Prompt + Skill + 测试输入] --> B[执行与评分]
  B --> O[失败证据驱动 Skill 修改]
  O --> C[候选重跑日常测试集]
  C -->|用户继续优化| O
  C --> V[独立验收集配对评测]
  V -->|accept 后用户应用| P[新的当前 Skill]
```

## 术语

| 概念 | 用途 | 是否由优化器修改 |
| --- | --- | --- |
| Prompt | 执行角色、通用约束和流程要求 | 否 |
| Skill 包 | 主技能分发与子技能业务规则、工具参数说明 | 仅允许的已有 Markdown 文件 |
| 执行环境 | Prompt、模型连接、评分、加载及运行参数的版本快照 | 否 |
| 测试案例 | query、context、预期与模拟返回 | 否 |
| expected | 评分答案：动作、路线、工具序列及参数 | 否；执行模型不可见 |
| fixture | 按工具名和可选参数条件匹配的模拟响应 | 否；命中后的返回进入执行循环 |
| 日常测试集 | 日常评测、修改与重跑使用的数据，内部名 optimize | 否；允许向优化器提供证据 |
| 独立验收集 | 检验候选是否改善，内部名 validation | 否；不提供给优化器 |
| 最终测试集 | 额外的阶段留出检查，内部名 final_test | 否；不参与候选选择 |
| 基线 | 本次对照所用的 Skill 与执行结果 | 历史版本保持不变 |
| 候选 | 基于当前基线或前一候选生成的修改版本 | 可作为下一轮优化起点 |
| 当前版本 | 项目默认执行使用的已发布 Skill 指针 | 验收后由应用操作切换 |

“业务输入只有 Prompt 和 Skill”指业务执行规则的来源，不代表评测无需测试集，也不代表无需配置模型地址和凭据。平台通过通用 call_tool 接收业务工具名与参数，不要求另配 Tool Schema。

## 三类模型各做什么

- **业务模型**：加载 Skill，判断路线、动作和工具参数，接收工具返回继续执行。
- **评分模型**：只判断配置为语义比较的参数值；路线、工具名、次数和结构由代码判断。严格或宽松比较不需要评分模型。
- **优化模型**：读取日常集的失败证据、少量通过样例及可编辑 Skill，生成一个局部补丁。

三类模型可以分别配置。同型号执行与评分适合跑通流程，但不能视为独立模型复核。规则修复和离线演示模型是另外的执行方式，必须与真实模型结果区分。

## 什么才算完成

| 状态 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 模型连接成功 | 当前连接能返回一次模型响应 | 完整 Skill 能成功执行 |
| 案例执行结束 | 已有可评分的执行证据，或明确的失败 | 业务参数一定正确 |
| 日常测试提升 | 候选对已知案例更好 | 未见场景也更好 |
| 独立验收 accept | 满足冻结的接受规则 | 已应用到项目或外部生产系统 |
| 应用完成 | 平台当前 Skill 指针已切换 | 外部 Agent 已部署更新 |

应用前仍检查版本与包完整性，冲突会拒绝覆盖。历史运行绑定原 Skill、环境和数据，不随当前版本改变。

## 当前范围

支持 PC 本地项目、模型 HTTP/WS 接入、渐进加载、fixture 工具模拟、案例评分、单候选优化、多轮手动继续、独立验收、应用与恢复。不会执行包内任意脚本或真实生产业务服务，不进行自动无限轮搜索。

参数准确率来自测试集和评分规则，不能单凭工具返回成功或最终回复流畅判定。合成示例上的提升也不能推断为真实图像效果或生产业务质量提升。
