## D01：优化对象与迭代单位

**决定**：以 Skill 的分发和工具参数表现为优化目标；优化器对已有 Markdown 提出一个补丁，通过静态检查后重跑。用户可从候选继续下一轮，平台不自动无限搜索。

**原因**：单候选与局部修改使提升可归因、差异可审查，避免同时修改模型、Prompt、答案而无法比较。

**约束**：不训练模型，不由优化器改 Prompt、manifest、脚本或测试数据；没有失败证据时不伪造提升。模型生成失败后的规则回退须明确记录，不能称为真实模型优化。

参考：[核心概念](../CONCEPTS.md)、[模块契约](../CONTRACTS.md)。

## D02：Prompt + Skill 定义业务执行规则

**决定**：工具用途、名称、参数、默认值、澄清与错误处理写在 Skill 内；原生工具通过固定 call_tool(name, arguments) 入口承载。模型连接配置与评测数据仍独立存在。

**原因**：再维护一份环境 Tool Schema 会造成重复配置和规则漂移，增加日常操作成本。

**约束**：运行时检查通用封装，评分按 expected 与规则检查；不宣称能从任意 Markdown 自动证明参数合法性。不能从测试答案或 fixtures 反推出模型可见的工具说明。

参考：[执行机制](../PROMPT_SKILL_EXECUTION.md)、[输入规范](../INPUTS.md)。

## D03：日常迭代与正式验收分开

**决定**：evaluate/baseline/optimize 使用日常集，内部字段仍叫 optimize。优化成功后只是候选完成重跑；validate(source_run_id) 才使用 validation 配对评测，并按 accept-v1 决定接受与否。final_test 作为额外留出，不参与候选选择。

**原因**：日常只需一套测试数据便能启动迭代；正式应用需要未参与优化的证据，避免把对已知答案的适配当作泛化提升。

**约束**：普通评测不强制要求验收集。验收默认两版本各 3 次，至少 3 次完整配对才满足证据门槛。R/A 不降且至少一项提高、J 不降、无关键回归及基础设施/完整性错误才可 accept；日常全通过不能绕过验收应用。

参考：[运行模式与隔离](../DAILY_TEST_AND_ACCEPTANCE.md)、[评分规则](../SCORING.md)。

## D04：输入隔离与候选来源链

**决定**：执行模型看不到 expected；优化器只看日常失败与少量通过样例。继续优化保留来源链，正式验收始终比较原始 root 基线和选定候选。

**原因**：防止答案泄漏，也防止连续优化只比较最近一小步而掩盖累计退步。

**约束**：验收检查案例 ID、归一化 query、group 与来源链日常/最终数据重叠。它不能自动证明语义独立；人工看过验收答案再调 Skill 后，不能继续声称这是未见数据。

参考：[数据隔离](../DAILY_TEST_AND_ACCEPTANCE.md)、[真实模型教程](../REAL_MODEL_WALKTHROUGH.md)。

## D05：渐进式加载有真实的后续推理机会

**决定**：select_skill 选择时直接返回正文；read_skill 用于额外引用。首次加载正文的同批业务调用/finish 暂不执行，模型收到新正文后再生成调用；已在上下文中的缓存/预加载不额外等待。

**原因**：避免多一次纯读取往返，同时保证“读取技能后调用”不只是事件排列好看。

**约束**：每次模型请求前检查累积上下文，超限明确失败，不静默删历史破坏工具关联。只能证明正文被提供给模型，不能证明模型内部确实采纳；效果靠调用与参数评测判断。

参考：[执行机制](../PROMPT_SKILL_EXECUTION.md)；演进证据：[选择自动加载](../SELECT_LOAD.md)、[渐进循环约束](../PROGRESSIVE_LOOP_2026-10-27.md)。

## D06：用 fixture 验证调用协议

**决定**：业务调用匹配固定模拟返回，未匹配记录 fixture_miss，保留已尝试工具名和参数。预期调用自身缺少可用返回时在预检阻止；实际偏离预期导致未命中仍作为能力失败记录。

**原因**：重复评测需要可控反馈，不能每次在外部系统创建任务、修改图片或产生其他副作用。

**约束**：expected 管“应怎样调用”，fixture 管“调用后返回什么”，不能把成功响应当成评分通过。模拟验证不等于真实任务系统或图像质量验收。

参考：[输入规范](../INPUTS.md)、[业务链路展示](../BUSINESS_TRACE_VIEW.md)。

## D07：评分与执行证据分层

**决定**：R/A/J 分别计分。路线、工具序列与字段结构由代码比较；语义规则下的参数值才交给评分模型，ID/枚举等可单独严格比较。finish 默认作为协议状态独立记录。

**原因**：不能因结束形式或一句成功回复，否定正确的业务调用或掩盖错误参数；自由文本也不应只能逐字匹配。

**约束**：环境启用语义却未配置模型会预检阻止；评分请求失败按基础设施错误处理。当前仅案例级启用语义且没有 judge 时仍可能宽松回退，这是待补齐的预检边界，见[评分限制](../SCORING.md#案例级语义规则的当前限制)，不能把回退成绩当成模型判定。基础设施错误单独统计并阻止接受；无有效分母显示未评估。工具返回和最终回复用于解释，不直接参与参数评分；历史展示恢复不改写原成绩。

参考：[评分规则](../SCORING.md)、[模型输出](../MODEL_OUTPUT_VISIBILITY.md)。

## D08：版本与原子应用

**决定**：已发布 Skill、环境、数据和运行快照保持证据；修改走草稿/新版本。应用、保存与发布在相应入口使用期望版本或 hash 进行原子比较，冲突拒绝覆盖。

**原因**：保证成绩对应明确输入，并防止并发编辑和过期候选覆盖新的工作。

**约束**：应用只切换平台当前 Skill，不部署外部服务；恢复也只切换指针，历史运行不删除。数据库升级先备份，不能通过删库解决旧字段约束问题。

参考：[数据集编辑](../DATASET_EDITING.md)、[架构](../ARCHITECTURE.md)、[部署](../DEPLOYMENT.md)。

## D09：移除总预算配置

**决定**：移除运行总 Token、金额、总时长预算及其拦截，旧列由启动迁移处理；保留实际用量统计、请求和案例超时、调用次数、上下文上限与取消。

**原因**：当前产品聚焦执行、评分和优化闭环，避免预算配置增加操作负担。

**约束**：取消预算不意味着可以取消循环终止和超时保护。没有价格配置时费用未知，不能写成零成本。历史记录中的预算条目不代表当前配置仍存在。

参考：[部署](../DEPLOYMENT.md)、[变更记录](../../CHANGELOG.md)。

## D10：PC 与本地部署优先

**决定**：原生 ES Modules 页面、Starlette、SQLite、进程内 Worker；面向 PC 单用户本地工作。业务链路突出加载子技能和调用工具，内部协议放详情，SSE 与持久化事件支持查看过程。

**原因**：降低部署及使用成本，使用户集中判断 Skill 是否改进。

**约束**：不把本地状态、历史截图或内置 demo 成绩当作其他部署的证据；不宣称已有多租户权限或生产工具执行能力。运行状态、验收结论、已应用状态分别呈现。

参考：[架构](../ARCHITECTURE.md)、[部署](../DEPLOYMENT.md)、[使用指南](../USER_GUIDE.md)。

## 如何变更决策

有新的明确需求时，先核对受影响的执行、评分、数据隔离与历史版本行为，再同步实现、回归和本文。说明新决定替代哪个旧约束以及原因；不静默删去旧理由，也不为了一个演示通过而放宽接受规则。

本索引只记录长期决定；任务进度、单次运行数据和测试数量写在交接信息或[验证记录](../VERIFICATION.md)。返回[文档导航](../README.md)。
