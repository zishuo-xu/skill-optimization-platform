# 使用指南：从项目到验收应用

本指南面向 PC 页面操作。首次启动见[首页](../README.md)，可直接导入的真实模型练习见[完整教程](REAL_MODEL_WALKTHROUGH.md)。

首次体验可直接进入列表置顶的「入门引导：任务协作」，点击「从这里开始」。Skill、测试数据和 Prompt 已备好，先配置并发布业务、优化和评分模型，再依次运行基线、优化重跑、独立验收、应用候选。页面下一步提示根据实际运行状态变化，示例不会自动调用模型或带入历史成绩。应用后显示「本轮闭环已完成」并提供验收结果入口；回滚或更换输入后重新按当前状态引导。运行结束时可通过「查看结果与下一步」进入结果概览。

## 1. 建立项目与输入

在「全部项目」新建项目。一个项目对应一套待优化 Skill，不要把无关业务混在同一组评测中。

1. 「Skill 包」：导入 ZIP，检查主 SKILL.md、子技能 ID 和文件路径。主技能描述选择与编排，子技能描述工具名、参数、默认值、澄清和错误处理。
2. 「Prompt 与模型」：填写业务 Prompt，接入业务模型；需要自动生成修改时再接入优化模型。配置语义评分时必须接入评分模型。
3. 「数据集」：导入 JSONL/JSON，默认选择「日常测试集」，查看预检结果再发布。

工具规则写在 Skill 内，不需要额外工具协议配置。案例上下文放在顶层 context；预期答案和 fixtures 分别用于评分和模拟响应。具体格式见[输入规范](INPUTS.md)。

已发布内容只读。修改 Skill、Prompt/模型或数据时创建草稿、保存、发布新版本，避免让旧成绩对应的输入发生变化。

## 2. 先验证接入，再试跑

每个模型分别测试连接。连接成功只验证一次模型响应，不能代替案例执行。评分模型使用流式网关时，检查其自身的流式配置，业务模型成功不说明评分模型也已配置正确。

在数据集选一个案例试跑：确认加载了正确子技能、产生了实际业务调用、参数和返回可查看，再检查评分。自由输入试跑没有预期答案，只观察行为，其工具响应是占位模拟返回。

试跑不写入正式运行指标，适合检查 Prompt、加载路径、fixture 和连接。不要把一次试跑通过当成整批验收。过程展示以「加载子技能」「调用工具」为主，模型请求、call_tool 封装和 finish 在内部协议详情中。

## 3. 跑日常测试建立基线

回到工作台，点击「运行测试集」，核对 Skill、环境和数据版本后启动。普通评测与基线评测都只跑日常测试集，不需要预先准备独立验收集。

在结果页先看整体通过率，再打开失败案例：

- 选错技能：检查主技能分发规则、适用条件和冲突意图。
- 参数不符：查看预期与实际的字段、值和比较依据，不只看工具名称。
- 澄清不符：检查缺失字段与是否不应发起业务调用。
- 模型/平台错误：先修正连接、超时或评分模型问题，再判断能力。
- fixture_miss：查看实际工具参数与 fixture 的 name、match、consume；工具尝试仍会保留，缺返回不等于未调用。

工具返回和最终回复是执行证据。参数错误时，即便模拟工具返回成功，案例仍应不通过。评分口径见[评分规则](SCORING.md)。

## 4. 优化并审查候选

点击「根据测试结果优化」，固定使用这次测试记录作为来源。完整且兼容的结果直接进入错误分析；只调整优化模型或其超时不会重跑业务测试。修改 Skill、执行 Prompt、业务模型、评分/执行配置或日常案例内容后需重新测试。缺失或基础设施错误的结果只补测对应案例及重复次数；补测仍失败时暂停优化，不让优化器修复连接问题。优化模型只接收日常集证据和可编辑 Skill，不接收独立验收或最终测试样本。

候选通过静态检查后在同一日常测试集重跑。结果页查看：

1. 「文件差异」：改了哪些通用规则，有没有把某个问题或答案硬编码进去。
2. 「案例对比」：哪些修好了、哪些变差、哪些仍失败。
3. 「运行记录」：是否真的调用优化模型，是否出现 fallback_started 或规则修复。

若出现「补丁应用失败」，直接看具体文件、修改序号和匹配原因；「文件差异 → 未应用的候选补丁」可展开、复制每条修改的完整 `search`、`replace` 和检查详情。也可到「运行记录 → 全部记录（包含优化器事件）→ 优化器返回内容 → 查看模型输出」查看完整输出，与本轮绑定版本的原文对照。换行或空白诊断不代表补丁已自动修复。

`fixture_miss` 也可能是测试缺少 Skill 要求的前置查询。应先核对业务调用顺序和版本能力约束；不能仅为匹配模拟返回，删掉必需查询或假定所有设备支持某种参数。优化器提示已要求将这类证据冲突报告为 `dataset_issue`，这属于提示约束，仍需审查候选是否遵守。

当模型明确归因为 `dataset_issue` 且未提出修改时，平台保留诊断并停止，不再用规则回退修改 Skill。查看「文件差异」中的诊断，核对测试预期、模拟返回和 Skill 规则后，修正相应草稿、发布并重新测试；模型的归因需要核实。

没有失败案例时不会伪造优化候选。优化失败或回退都应留痕；只有在真实模型生成了补丁且未回退时，才能声称是模型优化。

日常重跑完成后，候选还未被应用，也不产生正式接受结论。可点击「基于此候选继续优化」启动下一轮，直接复用上一轮候选的复测结果；条件变化时先补测。结果页的「准备测试结果」显示来源链接、Skill、复用和需执行数量；运行记录明确是否调用了模型。平台保留候选来源链，正式验收仍与该链的原始基线对照。

## 5. 独立验收

准备一批未参与日常调试和优化的案例。导入为「独立验收集」，或将显式包含不同 split 的完整文件按「保留文件划分」导入。日常数据已存于来源运行快照，可后补验收数据，不必为了启动普通评测而提前拆分。

从选定候选的结果页点击「独立验收」。平台绑定来源候选、原始基线与环境，冻结本次验收数据；默认每个案例对两版本各跑 3 次。

如果只是发布了新的优化模型配置（如超时、模型或流式开关），已有候选仍可继续验收，不必重新生成候选。业务 Prompt、业务模型、加载/执行/评分/验收配置必须与来源一致；验收会冻结当前环境并完整重跑，历史运行不变。验收排队后再发布环境则需重新启动验收。

会检查验收案例与来源链中的日常/最终数据是否在 ID、归一化问题或 group 上重复。该检查不能识别所有语义改写，仍需要人工独立设计。不要根据验收答案反复调 Skill 再把同一集合当作未见数据。

accept-v1 要求 R、A 均不下降且至少一项提高，J 不下降，没有关键案例回归、基础设施或完整性错误，配对验证完整。缺证据为 inconclusive，持平或退步不自动接受。详见[运行模式与隔离](DAILY_TEST_AND_ACCEPTANCE.md)。

## 6. 应用、恢复与导出

验收通过后点击「应用候选」，确认版本对照。平台校验当前版本与验收绑定的基线仍一致，成功后仅切换项目当前 Skill 指针；不会部署到外部 Agent 或任务系统。

若出现版本冲突，先刷新并核对变化，不要强行覆盖。已应用候选可通过「恢复应用前版本」恢复指针；旧运行保留原始快照和结果。需要给其他系统使用时导出 Skill ZIP，再按该系统的部署方式发布。

最终留出集用于额外阶段检查，不参与候选选择，也不能代替独立验收的应用门槛。当前平台保留该运行模式；接口见 [API](API.md)。

## 7. 跨环境排障与 AI 分析

遇到运行错误时，进入运行详情的「运行记录」，在顶部「AI 分析」中补充问题描述并点击「生成 AI 分析」。它使用**项目当前发布的优化模型配置**；因此可先修复模型连接、发布新环境，再分析旧运行。报告同时记录原运行环境与本次分析环境，不会重跑案例或改变评分、候选和验收结果。

分析包含已确认事实、带置信度的可能原因、排查步骤及待补充信息。完成后点击「复制完整报告」或「下载报告」，将结论和证据一起交给其他 AI 或开发者。刷新页面仍可查看最新一次报告；重新分析另存新报告，旧附件保留。

没有配置优化模型、模型连接失败或运行尚未结束时，也可「复制诊断材料」或「下载诊断材料」。调用失败会显示并保存错误，不伪造 AI 结论或使用规则回退。运行结束（含失败、取消、中断）后才可请求 AI 分析。

证据包含版本/hash、模型连接摘要、运行指标、日常失败案例与事件片段，标明采样和截断；不读取原始请求/完整响应附件。独立验收与最终测试只提供汇总和事件元数据，不发送案例、答案或事件载荷。常见凭据自动脱敏，业务文本仍可能含敏感信息，复制前可展开完整报告检查。AI 诊断只是建议，不能替代现场检查、正式验收或真实业务验证。

## 常见疑问

运行记录出现 `fixture_miss` 时，先看具体分类。若是「工具调用参数不匹配」，表示实际调用未命中模拟条件，尚未取得本次业务返回；例如实际 `method` 与案例声明的值不同。页面会对照实际值、业务预期声明和模拟匹配条件。先核对 Skill 与业务要求：模型选错方法时修正 Skill 并重新评测；调用正确但模拟条件错误时才修正 fixture、发布新数据集。不要为了让报错消失而直接删除匹配条件。这个案例级失败不等同于整轮运行异常，也不是对真实业务结果的评价。

| 问题 | 处理 |
| --- | --- |
| 为什么工具返回成功，评分却失败？ | 工具返回与 expected 比较是两件事，检查路线和参数差异 |
| 为什么日常全通过还不能应用？ | 需要独立验收达到 accept，不能用已知数据替代未见数据 |
| 为什么没有 finish 也能通过？ | 默认业务结果独立评分；严格结束协议才将缺少 finish 单独作为协议失败 |
| 为什么加载子技能后还有一次模型调用？ | 模型需要读取新加载的规则再生成业务参数；select_skill 已返回正文，无需重复 read_skill |
| 改了数据或评分规则，旧结果会更新吗？ | 不会；发布新版本后重新运行，新旧结果分别绑定各自快照 |
| 运行一直排队怎么办？ | 检查 Worker 和启动日志；见[部署排障](DEPLOYMENT.md#9-常见问题) |
